# [ 260928 0312 Codex (Dental 모듈 가중치 전수조사) ]

## 요약 판단

**각 모듈의 가중치가 올바르게 학습·검증되어 현재 코드에서 의도한 모델로 쓰인다고 볼 근거는 없습니다.** 전체 저장소를 대상으로 로컬 모델 파일, Git 추적/무시 상태, 체크포인트 내용, 학습 로그·평가 문서, 통합 Reader의 모델 경로와 로딩 코드를 대조했습니다. 사용 가능한 일부 바이너리의 SHA-256은 계산했고 실행 중인 파노라마 API에도 대표 원본을 넣어 결과를 확인했습니다.

핵심 판정은 다음과 같습니다.

- 현 PC에 실제 모델 바이너리가 존재하고 Reader 모듈 복사본도 바이트 단위로 같은 것이 확인된 것은 주로 Dental_002, Dental_008, Dental_012이며 Dental_013 ONNX도 로컬에 있습니다. 이것은 파일 존재와 복사본 동일성 증거이지, 임상적으로 잘 학습됐다는 증거가 아닙니다.
- 이 주요 바이너리들은 대부분 `.gitignore`의 `models/`, `weights/`, `*.pt`, `*.onnx`에 걸려 Git으로 버전 관리되지 않습니다. 다른 새 클론에서 같은 모델이 자동으로 준비되는지는 Reader의 `setup_env.py` 및 실제 로더 경로 불일치 때문에 보장되지 않습니다.
- Dental_008의 일부 `.pth`는 133~134바이트 Git LFS 포인터 문자열이지 모델 체크포인트가 아닙니다. 특히 유치 분류기 로더는 이 파일을 `torch.load`하다 실패해 `None`으로 돌아가며, 실패를 정상적인 “분류 안 함”처럼 처리합니다.
- Dental_004는 통합 코드가 기대하는 학습 체크포인트가 없고, Reader 초기화는 체크포인트가 없을 때도 무작위 초기화 모델을 반환합니다. Dental_003 통합 인터페이스는 모델 로더가 `None`을 반환하고 측정도 placeholder입니다. Dental_014는 현재 Reader 상태가 MOCK이며 실제 3세대 가중치 파일이 발견되지 않았습니다.
- 최근 Dental_015 사례 재실행에서 Dental_002 결과의 score가 FDI 매핑 과정에서 유실되어 API가 우식 32건을 전부 confidence 0.85로 꾸몄습니다. 따라서 현재 보이는 문제는 가중치 자체만으로 설명되지 않고, 후처리와 가중치-로더-API 결합 결함이 큽니다.

## 조사 범위와 판정 기준

조사한 저장소는 `Dental_000`~`Dental_015`, `Dental_Core`, `Dental_Panoramic_Reader`입니다. 바이너리 확장자는 `.pt`, `.pth`, `.onnx`, `.ckpt` 등을 조사하고 모델 생성·로딩 코드, 학습 기록, 기존 종합 벤치마크와 통합 서비스의 실제 모델 경로를 대조했습니다.

여기서 “파일 있음”은 바이너리 파일이 현재 로컬에 있는지, “로드 근거”는 서비스 코드가 그 파일을 찾아 실제 응답을 만드는 구조인지, “학습 품질 근거”는 같은 정확한 가중치 해시가 독립 평가 데이터의 정답·지표에 묶여 있는지를 뜻합니다. README 배지, ONLINE 상태, CI 통과, 파일 크기만으로 학습 품질을 PASS 판정하지 않았습니다.

### 무시되는 파일 및 LFS 포인터

가중치 폴더는 `.gitignore`의 `models/*`, `weights/*`, `*.pt`, `*.pth`, `*.onnx` 패턴에 대부분 걸립니다. 예를 들어 Dental_002의 `models/` 폴더는 Git ignored 상태이며 `best_patch.*`는 추적 파일 목록에 없습니다. 로컬 작업 트리가 `clean`이어도 이 파일이 원격 저장소에 커밋되어 있다는 뜻은 아닙니다.

`Dental_008/weights/pretrained/classifier_best.pth`는 파일 크기 133바이트이며 첫 줄이 `version https://git-lfs.github.com/spec/v1`, 내부에 표시된 원본 크기가 44,788,363바이트인 LFS 포인터입니다. `mask_rcnn_dentex_epoch_*.pth`들도 각 134바이트 포인터이며 내부 원본 크기는 약 185MB입니다. 이 로컬 파일은 `torch.load` 가능한 가중치가 아닙니다. 특히 유치 분류기 로더는 이 경로가 “존재”하므로 HF 대체 다운로드를 건너뛴 뒤 로드 예외를 잡아 모델을 `None`으로 만듭니다.

## 과거 성능 주장과 현재 근거의 차이

`Dental_000/reports/260903_2205_Dental_Modules_Comprehensive_Benchmark_Report.md`에는 일부 모듈의 높은 점수가 표에 있습니다. 이 조사에서는 그 표의 각 값이 현재 운영 바이너리의 SHA-256, 데이터셋 버전, 환자 단위 split, 임계값, raw prediction 및 집계 코드와 함께 재현되는지 확인하지 못했습니다. 특히:

- Dental_008의 종합표는 매우 높은 F1/민감도를 기재하지만 로컬 finetune `results.csv`의 마지막 validation 행은 BBox/mask precision 약 0.16, mAP50 약 0.23 수준입니다. 현재 운영 `yolov8m_best` 파일이 어느 학습 run에서 생성되었는지 기록이 없어 어느 수치가 해당 가중치를 설명하는지 확정할 수 없습니다.
- Dental_002의 실험 체크포인트와 운영 `.pt`가 같다는 것은 확인되지만, 최근 같은 파노라마 API 응답은 우식 32건/score 일괄 0.85/중복 치아 번호를 반환했습니다. 실제 score가 후처리에서 유실되므로 현재 통합 결과는 높은 성능 주장과 별개로 임상 사용 전 차단해야 합니다.

따라서 표의 지표는 “프로젝트 문서에 기록된 과거 주장”으로 두고, 해시 고정 운영 가중치의 독립 평가가 완료되기 전에는 현재 성능으로 홍보하거나 통과 판정하지 않아야 합니다.

### 단계 0 — 기준 가중치 동결 및 식별

1. 현재 각 서비스가 실제로 선택하는 파일의 절대 경로, SHA-256, 크기, 형식, ONNX 입출력/클래스, 모델 프레임워크 버전을 기록합니다.
2. 각 파일을 학습 run ID·데이터셋 버전·학습 스크립트 commit·export 스크립트 commit·원격 출처와 연결합니다. 연결이 되지 않는 모델은 `provenance_unknown`으로 격리합니다.
3. 운영 파일을 덮어쓰지 말고 해시가 고정된 읽기 전용 기준본을 따로 보관합니다. PT와 ONNX는 별도 모델 버전으로 등록하고 동등성 확인 전 서로 대체하지 않습니다.
4. Git LFS 포인터는 파일로 카운트하지 않습니다. 포인터 OID에 해당하는 실제 바이너리 존재와 다운로드를 검증하고, 실패 시 애플리케이션 시작 단계에서 중단되게 합니다.

### 단계 1 — 학습 성능을 가리는 통합 결함 우선 제거

재학습 전에 Dental_002가 confidence와 병소 좌표를 끝까지 전달하도록 고치고, 기본값으로 점수를 만들어 넣지 않습니다. Dental_009는 제3대구치 존재와 매복 상태를 별도 판정하며, `Fully Erupted`를 매복으로 넣지 않도록 합니다. Dental_013은 모델이 실제로 학습된 task에 맞는 입력을 받고, 결과 타입·좌표가 SSOT 계약과 일치하게 만듭니다. Dental_003 placeholder와 Dental_004 무작위 모델 로드는 진단 결과처럼 노출되지 않게 중단합니다.

### 단계 2 — 해시 고정 독립 재평가

1. 환자 단위로 train/validation/test를 분리하고 동일 환자의 양측·다른 시점·크롭 패치가 분할을 넘나들지 않는지 확인합니다.
2. 재학습과 threshold 선택에 쓰지 않는 잠금 test set을 준비합니다. 라벨은 치과의사 기준으로 버전 관리하고 불일치 조정 기록을 남깁니다.
3. 운영 환경과 같은 전처리·입력 크기·색공간·임계값으로 PT와 ONNX를 개별 평가합니다. 환자별 원시 예측 및 오류 이미지를 보관합니다.
4. 보고서 지표는 가중치 SHA, 데이터셋/split manifest, 평가 코드 commit, 모델별 threshold와 함께 출력합니다. 민감도와 정밀도, 특이도, F1 외에 환자당 false positive 수, 위치 IoU/Dice, FDI exact accuracy 및 신뢰구간을 목적에 맞게 기록합니다.
5. 이전 벤치마크의 점수를 똑같은 가중치와 split으로 재현할 수 없는 경우 기존 점수는 비교 기준에서 내리고 “재현되지 않은 과거 수치”로 표시합니다.

### 단계 3 — 선택 모듈 재학습

- **Dental_008:** 치아별 mask·FDI GT를 맞추고 전악/치열 누락, 겹침, 왜곡, 결손, 매복, 유치·혼합치열, 과잉치 사례를 명시적으로 나눕니다. 과잉치를 32개 FDI 중 하나로 강제 귀속하지 않고 별도 클래스/개체로 다룰지 라벨 정책을 먼저 정합니다. Segmentation 지표와 FDI 번호 정확도를 별도로 학습·검증합니다.
- **Dental_002:** 개별 우식 병소 bbox/mask가 치아 전체 박스와 혼동되지 않도록 라벨을 감사합니다. 정상 치아, 수복물, 치간 중첩, 해부학적 방사선 투과, 인접치 병소를 hard negative로 포함합니다. 환자 단위로 crop이 누수되지 않게 하고 병소 검출과 치아 FDI 연결을 별도 측정합니다.
- **Dental_012:** 실제 치근단 병소 외에 이공·상악동·비강저·절치공 등 유사 투과상 음성군을 포함하고, 병소 위치/치아 연결을 평가합니다. 고정 threshold 한 개로 지표를 맞추지 말고 임상 목표에 따른 sensitivity/precision 절충을 사전에 정합니다.
- **Dental_013:** 먼저 task를 전체 영상/치아 crop 분류/수복물 픽셀 검출 중 하나 또는 명시적 조합으로 확정합니다. Crown, filling/inlay, implant, RCT 등 class definition과 치아 귀속 GT를 확정한 뒤 #16/#26/#36/#46 같은 금속·비금속 충전물 및 정상 음성 치아를 포함해 학습합니다.
- **Dental_005/014:** 파노라마 모델과 학습 데이터를 공유하지 않는 별도 트랙입니다. 005는 구강 사진 도메인의 외부 촬영 조건을 포함하고, 014는 독립 DEXA 기준과 임상 코호트 설계를 확보한 이후만 진행합니다.

작은 증강 데이터만으로 조기 종료한 모델을 새로 만드는 대신 환자·기관·촬영 장비의 분포를 포함하는 독립 데이터와 누수 차단을 우선합니다. 목표는 높은 train/validation 숫자가 아니라 잠금 test와 외부 기관에서 유지되는 오류율입니다.

### 단계 4 — 재학습 승인 기준과 배포

각 모듈은 학습 전 안현찬 치과의사가 임상적으로 필요한 operating point를 확인하고, 그 목표에 맞춘 승인 기준을 고정합니다. 기존 프로젝트의 민감도 90%·정밀도/특이도 80% 목표는 후보 출발점일 뿐 모든 모듈에 그대로 적용하지 않습니다. 치아 분할/FDI는 세그멘테이션 품질과 정확 번호율, 매복/과잉치는 상태별 오분류 및 유보율, 수복물은 클래스별 검출·위치 정확도로 별도 합의합니다.

최종 배포 전 아래 조건을 전부 확인합니다.

- 잠금 환자 단위 평가가 사전 승인된 지표 기준을 통과하고 주요 클래스의 신뢰구간/오류 유형이 공개됨.
- 모델의 실제 서비스 입력/전처리와 학습 평가 입력이 일치함.
- 변환된 ONNX와 원본 PyTorch 모델의 결과 차이가 사전 허용 범위 이내임.
- API 결과가 confidence·좌표·class·FDI를 임의 기본값 없이 보존하고, 동일 해시 원본 위에 같은 객체를 표시함.
- 실패·저신뢰·입력 분포 이탈 상황에서 확정 판정을 내지 않고 검토 필요 상태로 유보함.
- 새로운 가중치는 새 SHA-256과 버전을 부여하며, 이전 가중치로 되돌리는 절차와 검증 기록이 있음.

## 권고 실행 순서

- **Dental_002 신뢰도 전달:** pipeline의 `_map_lesions_to_fdi`가 detector의 `scores`를 lesion에 전달하고 API는 누락 시 0.85 대신 0.0을 쓰도록 바뀌었습니다. 이는 이전에 관찰된 모든 우식 소견이 0.85로 출력되던 신뢰도 왜곡을 줄이는 올바른 수정입니다. 다만 pipeline은 detector `scores` 배열에 해당 인덱스가 없으면 여전히 `0.5`를 대신 넣습니다. 이 경우도 실제 모델 score가 아니므로 데이터 누락 상태를 명시하거나 해당 결과를 격리하는 후속 수정이 필요합니다.
- **Dental_003 상태 표시:** 가짜 `rbl_ratio: 0.0` 결과 대신 `UNIMPLEMENTED_MODEL` 빈 결과를 반환하고 health를 `STANDBY`로 바꾼 것이 확인됩니다. 단, 임상 bone-loss 기능이 구현·검증된 것은 아닙니다.
- **Dental_004 초기화 차단:** 지정 위치와 setup 경로 양쪽에서 체크포인트를 찾고, 로드가 안 되면 `None`을 반환하며 입력 원본을 보존합니다. 이전의 무작위 가중치로 초해상도 출력을 만드는 위험에 대한 적절한 fail-closed 수정입니다.

### 아직 해결 또는 검증 완료로 보기 어려운 점

1. **Dental_009 가드는 #18 정답을 같이 제외할 수 있습니다.** 이전 동일 영상 API 결과에서 #18은 `Fully Erupted / Vertical`, #38도 `Fully Erupted / Vertical`로 나왔습니다. 새 코드의 `is_normally_erupted` 조건은 이 둘을 모두 `impactedTeeth` 결과에서 제거합니다. 안현찬 선생님의 정답은 #18이 매복이므로, 현 eruption 휴리스틱이 틀린 상태에서는 #38 오탐을 막으면서 #18 정답도 놓칠 가능성이 높습니다. 더구나 #17 등 인접치가 없으면 코드가 `Fully Impacted`를 직접 만들고 결과에 포함하는 경로가 남아 있습니다. BBox 네 모서리로 장축을 추정하는 방식도 바뀌지 않았습니다. 그러므로 이 수정은 안전한 일차 필터이나 “실제 매복만 남긴다”는 임상 판정 완료 증거는 아닙니다.
2. **Dental_008 HF fallback을 “검증된 정식 가중치”라고 부를 근거가 추가되진 않았습니다.** `hf_hub_download` 호출에는 revision pin이나 예상 SHA-256 확인이 보이지 않습니다. 내려받은 체크포인트를 고정된 검증 바이너리라고 보장할 수 없으므로 출처·revision·digest 및 `load_state_dict` 성공을 모델 manifest로 확인해야 합니다.
3. **Dental_013 수복물 출력 계약은 이번 변경에 포함되지 않았습니다.** predictor는 여전히 `restoration_type`을 반환하고 BBox를 반환하지 않지만, `api_server.py`는 `type/class_name`과 `bbox/box`를 읽어 누락 박스에는 0 크기 박스를 만듭니다. Dental_015의 캔버스 레이어는 앞선 커밋에 존재하지만, 입력되는 수복물 결과가 0건이거나 위치·타입이 없으면 화면의 레이어만으로 수복물 미탐/위치 문제는 해결되지 않습니다.

# [ 260928 1008 Codex 임상 검토 도구 박스 정렬 원인 분석 및 랩탑 개발팀 개선 지시 ]

## 검토 결론

현재 화면에서 보이는 박스 불일치는 우선 **브라우저의 캔버스 축소 오차가 아니라, 도구에 직접 입력한 표본 박스 좌표 및 그에 붙인 치식·설명 오류**로 판단됩니다. 이 도구의 TheGem 원본은 1170×540이고 캔버스도 1170×540입니다. 이미지와 모든 박스를 동일 캔버스에 그려 축소하므로 현재 구성에서는 CSS가 박스만 따로 이동시키는 경로가 확인되지 않았습니다.

반면 `tools/clinical_criteria_tool/app.py`의 소견 박스들은 검증된 임상 어노테이션 파일이나 실제 런타임 응답을 불러오는 대신 `x`, `y`, `w`, `h`를 수동으로 상수 지정합니다. 예를 들어 치근단 박스 `x=0.779`, `y=0.772`, `w=0.025`, `h=0.058`은 원본 픽셀 기준 대략 `[911, 417, 941, 448]`이 됩니다. 이는 기록된 raw 검출 `[912, 417, 942, 448]`과 위치상 거의 같습니다. 따라서 빨간 사각형의 그리기 위치 자체보다, 샘플 어노테이션의 해부학적 정답과 치식 설명을 우선 재검증해야 합니다.

특히 이 박스는 화면 기준 영상 오른쪽 아래에 표시되는데 소스의 `fdi` 설명은 `46 or 47 apex`입니다. 일반적인 파노라마 좌우 표기 기준에서는 해당 위치와 우측 치식 설명이 서로 맞지 않을 가능성이 높습니다. 이 불일치는 좌표와 FDI를 함께 치과의사가 다시 확인해야 합니다. 이 표본 박스를 임상 정답 또는 모델의 정식 출력처럼 사용해 기준을 확정하면 안 됩니다.

## 랩탑 개발팀 개선 요청

1. **임의 좌표를 임상 표본으로 쓰지 않기**
   - 코드 내 상수 좌표를 검수 완료된 annotation JSON/CSV로 옮기고, 각 상자에 원본 이미지 ID·SHA-256·원본 너비/높이·좌표 체계·클래스·FDI·좌우·상태·주석자·출처를 기록합니다.
   - 원시 모델 출력, 예시용 그래픽, 치과의사 확정 정답을 서로 다른 레이어와 provenance 값으로 구분합니다. 아직 검수하지 않은 박스에는 `예시/미검증`을 화면에 명시하고 임상 기준 저장 시 확정 사례로 포함하지 않습니다.

2. **원본 이미지 좌표를 기준으로 그리기**
   - 저장 좌표는 원본 픽셀 기준 `[x1, y1, x2, y2]`로 통일하고, 화면 표시 직전에 한 함수에서 캔버스 좌표로 변환합니다.

3. **FDI와 영상 좌우를 별도 검증**
   - 화면에 환자 좌우 방향 표기를 보이고, FDI 번호는 박스의 영상 좌표와 별도 필드로 관리합니다.

4. **리뷰 화면에서 오차를 직접 고칠 수 있게 하기**
   - 원본 유지, 확대/축소·이동, 레이어별 표시/숨김, 박스 선택·이동·크기 조절, FDI·좌우·소견 수정, 변경 전후 비교를 제공합니다.

   - 현재 도구의 저장 버튼은 기준 정책만 저장합니다. 박스 위치를 검수·수정하는 기능이 없다면 이를 명확히 안내하고, 그 상태에서는 박스 배치를 사용자가 승인한 임상 라벨로 취급하지 않습니다.

## 2. 잔여 P0: TheGem 매칭 정책 및 통일 임계치 사전 고정

### 2.1. 공간 매칭 및 귀속 평가 분리 프로토콜
- 공간 매칭 임계치 (Spatial Matching Threshold):
  다중 모듈이 결합된 복합 검증(TheGem Composite)의 공간적 BBox 매칭 기준을 `IoU >= 0.25` 단일 임계치로 통일 고정합니다.
  - IoU >= 0.25 만족 시: 공간적 위치 검출 성공
  - IoU < 0.25 미만 시: 공간적 위치 검출 실패 (골드는 FN, 해당 예측은 FP)
- FDI 치아 귀속 일치율 (FDI Tooth Attribution Match):
  공간 매칭에 성공한 참양성(TP) 객체들을 분모로 하여, 해당 질환/상태가 귀속된 치아 번호가 골드 치식과 일치하는지 여부를 독립 평가 축으로 산출합니다 (`FDI_Match = 일치건수 / TP`).
- 일대일 매칭 (One-to-One Greedy Matching):
  단일 골드 박스에는 가장 높은 IoU를 기록한 단 하나의 예측 박스만을 1:1 매칭하며, 동일 치아/영역에 중복 탐지된 잉여 예측 박스는 전원 위양성(FP)으로 엄격히 집계합니다.
